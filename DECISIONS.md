# Журнал решений

Выборы с рассмотренными вариантами. Новые внизу. Пересматривайте свободно.

Журнал начат заново 6 ноября 2026, когда проект пересобрали из песочницы источников в каталог
проектов. Прежние 56 решений — в `DECISIONS.md` под тегом `v1-sandbox`; те из них, что
действуют дальше, перечислены в конце.

## 2026-11-06 — пересборка

1. **Тот же проект, а не новый.** Пользователю передали десятки репозиториев (GitHub `X-Keeper`,
   `imux-team`; GitLab `x-keeper-rnd`), и нужно одно место контроля и поиска. Реестр, раннер
   практик, секреты и MCP уже есть; новый проект начал бы с их переписывания. Код
   переписывается по месту, раскладка yaml-файлов проектируется заново.
2. **Четыре уровня: пространство → проект → репозиторий → сервис.** Репозиторий входит в один
   проект, проект — в одно пространство; общее использование выражается связями. Двойное
   членство вернуло бы дубли.
3. **Структуру задаёт пользователь, диск не парсится.** Отвергнуто: папка первого уровня
   `~/Projects` — пространство, промежуточные — группы. Решил пользователь. Поиск локального
   клона по `remote.origin.url` остаётся — это поиск места, а не структуры.
4. **Репозиторий опознаётся по адресу remote**, приведённому к `host/путь` в нижнем регистре
   без `.git`. В проект можно включить несклонированное; у другого разработчика пути другие, а
   адрес тот же. Код без git включается по имени папки, путь — в `local.yaml`.
5. **Источник — это сервис.** Отдельной сущности «источник» нет: Kafka и ClickHouse — сервисы
   инфраструктуры `hyper-imu`, Postgres X-Keeper и MoySklad — сервисы без репозитория.
   Пересматривает прежнее «центральная сущность — источник, не проект».
6. **Знание разделено по виду: данные — в репозитории пространства, тексты — в
   `<проект>-docs`.** Рассмотрено пять вариантов: один общий реестр (нельзя передать проект,
   X-Keeper и SphereTele смешаны); репозиторий на проект со всем внутри (общему сервису нужен
   проект-«хозяин», ссылки ведут в чужие репозитории, правка раскладки — 15 коммитов); внутри
   репозиториев кода (пишем в чужое, внешним сервисам жить негде); репозиторий на пространство;
   и выбранный — репозиторий на пространство для сервисов, связей и практик плюс `<проект>-docs`
   для текстов. Довод: граф сервисов пересекает проекты (SSO X-Keeper нужен шести репозиториям),
   резать его по проектам — резать там, где связей больше всего. Из репозитория пространства
   проект позже выделяется с историей (`git subtree split`), обратно склеивать труднее.
7. **Идентификатор сервиса уникален по всем пространствам**, путь «пространство/проект/сервис»
   — только для показа. Ссылки `use("xkeeper-pg/device-info")` и метки в скопированном коде
   остаются как были. Идентификаторы проектов и условий тоже глобальны.
8. **Один сервис — много имён.** У сервиса список других имён (compose-сервис, хост); имена
   переменных, под которыми вызывающий держит его ключи, записаны в связи. Найденная в проекте
   ссылка сопоставляется по адресу, потом по значению секрета, потом по имени. Сканер по новому
   имени сервис не создаёт: несопоставленное пользователь привязывает сам.
9. **Практика принадлежит сервису, к которому обращается** (скачивание из XKDB — у XKDB).
   Связь хранится у вызывающего и может ссылаться на практику; обратная сторона вычисляется.
10. **У сервиса несколько точек входа.** `xkeeper-pg` — один сервис с одной учёткой и точками
    `logistic`, `panel`, `accounts`, `devices`; связь и условие могут указывать точку.
    Отвергнуто: сервис на каждую базу — одна учётка повторилась бы четыре раза.
11. **Условие — именованное и заводится один раз.** «База устройств требует корпоративной сети,
    XKDB — нет» — знание, которое нельзя выкинуть (решил пользователь). Условие отдаётся агенту
    до первой попытки запроса и проверяется перед запуском практики. Проверка адреса у условия
    необязательна: условие без неё — объявленное знание с подсказкой.
12. **Связи выводятся и записываются в файлы.** Из compose и `.default.env` / `.env.example`
    выводится большинство рёбер; принятые пишутся в `links.yaml` с указанием, откуда. Отвергнуто:
    вычислять на лету — репозиторий пространства должен читаться без приложения. Нарисованная
    вручную схема устаревает (`imu-sphere/docs/infra-map.html`).
13. **Узел карты — сервис**, проект визуально объединяет свои сервисы. `hyper-imu` — 15 сервисов,
    ребро «`hyper-imu` → `wifi-locator`» не говорит, кто ходит.
14. **Главный читатель — агент.** Всё, что видно в окне, доступно через MCP. Карта как картинка
    нужна позже — для объяснения и передачи другим разработчикам.
15. **«Не распределено» ничего не решает.** Список из `gh`, `glab` и локальных клонов, из
    которого пользователь назначает проект; подгруппа GitLab — только подсказка имени.
    Пространство не равно хостингу: `x-keeper-rnd` идёт в `X-Keeper` рядом с GitHub.
16. **К хостингам ходим через `gh` и `glab`**, как раньше к Docker через `docker`: вход хранится
    у утилит, токены в `secrets.json` не нужны.
17. **Действия над репозиториями — чтение и «открыть».** Без `pull`, `push`, `compose up`.
18. **`practices.yaml` в репозиториях кода больше нет.** Что репозиторий использует и под
    какими именами — связи его сервисов. Иначе одно знание в двух местах.
19. **Правка агента — незакоммиченное изменение в репозитории пространства**, которое
    пользователь смотрит диффом и принимает. Заменяет автопринятие предложений (прогон двух
    версий, сравнение хэшей, экран ревью): ~400 строк ради трёх предложений за всё время.
    Заметки и описания полей коммитятся сразу, и только свои файлы — общий `git add -A`
    заодно принял бы чужую непросмотренную правку.
20. **Документацию пишет агент, проверяет пользователь.** Первое наполнение помечается
    «сгенерировано»; приложение показывает устаревание (в коде есть коммиты новее правки
    карточки). Руками её никто вести не будет.
21. **Данные прежнего реестра переносятся вручную, один раз**, без кода миграции; до переноса
    установленный CLI остаётся старым.
22. **Монитор отложен.** Полезным, как ожидалось, не оказался (приложение не запущено,
    последнее падение в журнале — 1 октября). Код на месте, не развивается.
23. **Проекты вкладываются** (уточнение п. 2). `scada`, `erp`, `mes` — полноценные проекты со
    своими репозиториями, и все относятся к `x-factory`; решил пользователь. Сделано полем
    `parent` в `project.yaml`, папки проектов остаются плоскими (`projects/<id>/`), глубина не
    ограничена. Отвергнуто: отдельный уровень «группа» между пространством и проектом (ещё
    одна сущность ради того же) и вложенные папки (перенос проекта к другому родителю менял
    бы пути всех его практик).

## Действует из прежнего журнала (`v1-sandbox`)

Номера — прежние.

- 1 — нативное SwiftUI, не локальный веб. 2 — не Postman: практика — ячейка кода с запуском.
- 3, 4 — секреты без шифрования в `secrets.json`; агенту значения не отдаются.
- 5, 41 — «встроить» = скопировать код с меткой; копия «изменена», если не содержит тело версии.
- 6 — ядро `PracticesCore` с CLI + приложение через xcodegen. 11 — данные в `~/.practices/`.
- 20, 33 — связка — код с `use()`; async-практики идут через фоновый event loop.
- 23–25 — документы и словарь полей у сервиса; схема результата с каждого прогона; поиск по смыслу.
- 27, 28 — цель — `address` или `url`, шаблоны над ключами; `run` делает `execvp`, конфликт
  значений одного ключа — ошибка.
- 29 — Doctor ищет секреты своим однопроходным поиском. 30 — HTTP без TLS разрешён.
- 31, 42 — версия практики = номер коммита её файла; пустая история — ноль версий.
- 32 — практики самодостаточны: подключение повторено в каждой.
- 34–36 — маскируются только секретные значения ≥ 6 символов; в истории прогонов нет данных;
  числа JSON читаются как Int64.
- 37 — MCP-сервер — тот же `practicesctl`, stdio. 40 — `describe_field` не перезаписывает.
- 48 — реестр пишет env-файлы проектов точечно; файл под git секретов не получает.
- 54 — `install.sh` удаляет бинарник перед копированием. 56 — проверки только по запросу.
